# Technical Feasibility Assessment — Historical Baseline (2026-10-28)

> **Historical import, not generated by the new Skill workflow.** This summarizes the previously discussed static review of the project and the `better-auth/better-auth` `v1.7.11` source tag. The exact historical repository commit and installed Ubuntu package files were not verified. Revalidate before use; recommendations below are **not approved product decisions**.

## Scope and evidence

Investigated three gaps from Contract v1.1: wallet-address OIDC subject, SIWE-only session enforcement, and SIWE-authorized one-to-many OAuth client ownership. The project lockfile resolved `better-auth`, `@better-auth/core`, and `@better-auth/oauth-provider` to `1.7.11`. Upstream source: [Better Auth OAuth Provider v1.7.11](https://github.com/better-auth/better-auth/tree/v1.7.11/packages/oauth-provider/src).

## Summary

| Question | Historical conclusion | Evidence and limitation |
| --- | --- | --- |
| Public OIDC `sub = address` | **Unproven with supported public extension APIs** | Current resolver uses internal `user.id`. |
| SIWE-only session enforcement | **Conditionally feasible, not yet proven end to end** | SIWE creates normal Better Auth sessions, while other sign-in methods remain. |
| One verified wallet owns multiple OAuth clients | **Supported data model; missing wallet authorization boundary** | `clientReference`, `clientPrivileges`, and owner associations exist. |

## 1. OIDC subject mapping

**Verified in reviewed upstream v1.7.11 source:**

- `packages/oauth-provider/src/utils/index.ts:1069–1078`, `resolveSubjectIdentifier`: public subject defaults to `userId`; pairwise mode derives a per-client/sector value.
- `packages/oauth-provider/src/token.ts:326–400`, `createIdToken`: ID Token `sub` is derived from internal `user.id` through that resolver.
- `packages/oauth-provider/src/userinfo.ts:26–38,169–224`, `userNormalClaims` and UserInfo endpoint: default `sub` is internal ID; access-token subject is also used for internal user lookup.
- `packages/oauth-provider/src/token.ts:249–292`: JWT access tokens use `user.id`, or `clientId` for a client-only grant.
- `packages/oauth-provider/src/introspect.ts:406–425,498–522,632–657`: opaque token introspection uses internal IDs; the presentation layer supports built-in pairwise conversion.
- `packages/oauth-provider/src/token.ts:1800–1972`: refresh-token grant reloads the internal user and invokes ordinary token issuance, therefore ID Token subject resolution is reused.
- `packages/oauth-provider/src/authentication-context.ts`: `sub` is a reserved ID Token claim, not directly replaceable through `customIdTokenClaims`.

**Product versus standard:** OIDC requires stable subject semantics and UserInfo–ID Token subject agreement; it does not require Ethereum addresses. Address-based public subjects are the **product's** added requirement. Do not automatically require wallet `sub` in `client_credentials` machine tokens.

**Not established:** A safe *publicly supported* extension that converts both ID Token and UserInfo `sub` to wallet addresses without breaking internal lookups. Ideas such as changing the internal user ID, custom hooks, or a provider mapping layer must be validated rather than assumed feasible. Canonical address format and whether access-token/introspection subjects must also be addresses await approval.

## 2. SIWE-only authentication

**Verified in reviewed upstream v1.7.11 source:**

- `packages/better-auth/src/plugins/siwe/index.ts:63–85,96–240`: nonce handling and SIWE verification path.
- `packages/better-auth/src/plugins/siwe/index.ts:418–437`: after successful verification, `internalAdapter.createSession(user.id)` creates a standard session and sets a cookie.
- `packages/oauth-provider/src/authorize.ts:785–925`: the authorization endpoint checks for a valid Better Auth session and prompt requirements; it does not automatically establish that this session originated from SIWE.

**Project conflict:** `lib/auth.ts` had password, passkey, and SSO paths. Linked wallet records alone do not prove SIWE session provenance. A robust solution must address proof of authentication origin, legacy sessions, authorization-path enforcement, refresh-token lifecycle, and wallet switching. A logged-in session may be reusable if created from acceptable SIWE authentication. `client_credentials` is not end-user SIWE login.

**Not established:** a fully verified configuration-only/provider-hook solution. Framework extension mechanisms suggest feasibility, but negative-path and runtime tests were not run.

## 3. Wallet-based OAuth client ownership

**Verified in reviewed upstream v1.7.11 source:**

- `packages/oauth-provider/src/schema.ts:8–12,48–56`: unique `clientId`, non-unique user owner association.
- `packages/oauth-provider/src/register.ts:1279–1319`: managed client registration requires a session and records a user-based or reference-based owner.
- `packages/oauth-provider/src/types/index.ts:929–973`: `clientReference` and `clientPrivileges` are available for owner selection and policy checks.
- `packages/oauth-provider/src/oauthClient/endpoints.ts:21–137`: client management enforces owner association and can list multiple clients.
- `packages/oauth-provider/src/register.ts:300–341`: anonymous client registration depends on `allowUnauthenticatedClientRegistration`; an authenticated session or validated initial access token can authorize registration.

**Implication:** The one-wallet-to-many-clients data model need not be reinvented. However, a real wallet-owner trust boundary must ensure the management session originates from SIWE, privileged mutation paths enforce appropriate owner authorization, and any initial access tokens are governed by an approved wallet-based policy. Disabling open registration alone is not sufficient.

## Verdict and outstanding decisions

The Better Auth 1.7.11 stack appears to be a useful base, but is **only conditionally suitable** for Contract v1.1. The highest-impact unresolved feasibility question is how to generate an address-based OIDC public `sub` consistently through supported extension mechanisms. Remaining decisions: address canonicalization, EOA/ERC-1271 and chain policy, session provenance and wallet switching, owner representation, admin exceptions, and cross-token subject expectations.

**Use:** a research starting point, not implementation authorization or proof that a particular customization passes protocol/security tests.
