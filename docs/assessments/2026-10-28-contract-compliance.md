# Contract Compliance Report — Historical Baseline (2026-10-28)

## Assessment scope

Product Understanding Contract v1.1. Six areas: SIWE-only login, wallet address OIDC subject, one owner/multiple OAuth clients, authenticated registration, separation of identity roles, and OAuth/OIDC interoperability. Original inspection was static; no migrations, tests, deployed runtime configuration, or certification were verified.

## 1. SIWE-only authentication — Conflict

The earlier review found `emailAndPassword.enabled: true` in `lib/auth.ts` around line 110; `passkey()` around line 145; `sso()` around line 195; and OAuth `loginPage: "/sign-in"` around line 312. UI code under `sign-in-form.tsx` calls `authClient.signIn.email`. SIWE's `verifyMessage` exists in `lib/siwe.ts`, but the OAuth provider accepts general Better Auth sessions without proof that the **current** session originated from SIWE.

Risks: password-authenticated wallet-linked users may be treated as wallet-authenticated; session provenance, legacy sessions, wallet switching, and contract wallets remain unverified. `anonymous: true` in the SIWE plugin removes the requirement for a real email; it does **not** bypass signature verification.

## 2. Wallet address as OIDC subject — Conflict

The earlier review found Better Auth maps SIWE records to normal internal users; the OAuth provider derives ID Token and UserInfo subjects from `user.id`. A wallet address in a custom profile claim or login response does not satisfy `OIDC sub = address`. Standard custom ID Token and UserInfo claims cannot simply override the protected subject claim. Canonical address representation and consistent subject handling across issuance, refresh, and introspection were unresolved.

## 3. One owner, multiple clients — Partial

The framework has an `oauthClient` ownership association (`userId`), multiple-client listing by owner, permission checks, and a unique `clientId`. However, ownership was not required to come from SIWE authentication; unauthenticated registration could create clients without an owner. Owner isolation and actual database constraint enforcement were not executed as tests in the earlier assessment.

## 4. Unauthenticated OAuth client registration — Conflict

`lib/auth.ts` enables `allowDynamicClientRegistration: true` and `allowUnauthenticatedClientRegistration: true` (around lines 315–316). The registration endpoint accepts anonymous authorization-code client creation when that option is enabled. Restricting only the `client_credentials` grant is not enough. Contract v1.1 permits **authenticated** Dynamic Client Registration; it forbids the anonymous mode and requires wallet-authorized ownership.

## 5. Identity separation — Partial

Client owner ID, OAuth client ID, and authorization end-user ID are separate protocol roles, even when the same underlying Better Auth user model represents owners and end users. There was no proven wallet-to-chat/email service-account binding. SIWE-generated placeholder emails are not verified mailbox ownership; a separate SCIM/OIDC demonstration with `email_verified: true` was not demonstrated to represent a wallet-authenticated account.

## 6. Protocol interoperability — Partial / unverified

The earlier review found provider discovery routes and demonstration flows covering authorization code, S256 PKCE, state, nonce, consent, token exchange, refresh, and bearer UserInfo. Third-party clients use standard HTTP endpoints and need not adopt the IdP's frontend libraries. Runtime issuer alignment, TLS, JWKS, external-client validation, deployment CORS behavior, and complete conformance were not verified. A standards-valid internal-ID OIDC `sub` still violates this particular Product Contract.

Wallet B can authenticate into Wallet A's chat client: `sub` must be Wallet B's address while `aud` identifies `client-a-chat`. Wallet B gains no ownership rights over Wallet A's client.

## Product understanding verdict

The earlier Codex review correctly identified a **third-party-facing wallet-centric IdP** and distinguished SIWE authentication, wallet-based external user identity, OAuth clients, application ownership, and service-account bindings. The repository was not compliant with Contract v1.1 at the time of the review. The open decisions included canonical address format, EOA / contract-wallet semantics, OIDC subject mapping, SIWE session provenance, ownership enforcement, and wallet/session switching.
