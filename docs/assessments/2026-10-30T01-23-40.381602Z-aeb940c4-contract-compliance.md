# Contract Compliance Report

## Scope and evidence

The authoritative requirement source is `docs/PRODUCT_UNDERSTANDING_CONTRACT.md`, version **1.1**, especially sections 2–5. Applicable repository instructions and the contract-compliance skill were read before this investigation.

**Verification limits:** no tests, builds, migrations, installations, live endpoint calls, wallet operations, or deployment checks were executed. Existing assertions are test-source evidence, not passing tests. Only this new report is published; no application or configuration changes are authorized by this assessment.

## Findings

### F1 — Independent password and passkey authentication remain enabled

**Status: Conflict. Verified statically.** `authOptions.emailAndPassword` in `lib/auth.ts:110–120` enables password authentication, automatic sign-in, and password reset. The plugin list includes `passkey()` at line 145. The configured OAuth login page is `/sign-in` at lines 312–314.

`components/forms/sign-in-form.tsx:60–79` invokes `authClient.signIn.email`. `app/(auth)/sign-in/_components/sign-in.tsx:35–46,60–85` presents email login and independent passkey login. Existing tests explicitly expect successful password signup/sign-in in `lib/auth.test.ts:54–78`; those tests were not run.

**Contract mismatch:** P2 forbids password and passkey authentication as independent end-user login methods. The source configuration itself conflicts, regardless of whether a live instance was available for testing.

**Risk and limits:** Non-wallet identities can be admitted by the configured authentication system. Whether a particular deployment accepts them through all OAuth authorization paths remains untested.

SSO is additionally installed in `lib/auth.ts:195–300`. The SCIM OIDC provider is conditional at lines 296–298; `lib/scim-demo.ts:40–49` checks enablement and configuration. `resolveSCIMDemoSSOUser` returns `action: "continue"` for other providers (`lib/scim-demo-employee.ts:583–589`) and uses issuer/subject and provisioning links for its own provider (`593–641`), without SIWE proof in that resolver. Successful SSO and deployment reachability are unknown; configured SSO must not be mistaken for approved SIWE authentication.

### F2 — Unauthenticated client registration is explicitly permitted

**Status: Conflict. Verified statically.** `oauthProvider` in `lib/auth.ts:315–316` sets both `allowDynamicClientRegistration: true` and `allowUnauthenticatedClientRegistration: true`.

`app/api/auth/[...all]/route.ts:25–40` delegates to Better Auth handlers; the wrapper adds CORS headers and does not add wallet-owner authorization. `registerTestClient` in `app/client-test-siwe/oauth-flow.ts:96–113` calls the registration endpoint with ordinary public-client metadata.

**Contract mismatch:** P5 explicitly prohibits unauthenticated registration and requires wallet-owner authorization for registration and management. A public OAuth client having no client secret is a separate issue from whether its registration is authorized.

**Risk and limits:** The configured registration boundary permits ownerless or otherwise unapproved registrations. Endpoint responses, actual owner records, registration-access-token handling, and initial-access-token policy were not verified in upstream code or runtime.

### F3 — Account linkage substitutes for current-session provenance

**Status: Conflict. Verified statically for the UI; server acceptance remains unknown.** `WalletClientTest` computes `hasWalletSession` from the presence of a session and any linked account with `providerId === "siwe"` in `app/client-test-siwe/wallet-client.tsx:48–51`.

**Contract mismatch:** P2 explicitly says a linked wallet is insufficient evidence that the current session originated from SIWE. The predicate does not establish authentication origin, verification time, or the wallet authenticated by the current session.

The OAuth account selector lists device sessions without a visible SIWE-origin filter in `app/(auth)/oauth/select-account/page.tsx:12–29`. The provider's account-selection and post-login configuration (`lib/auth.ts:327–389`) concerns session selection and organization policy, not a demonstrated SIWE provenance boundary. `customSession` at lines 405–417 returns the session without adding an origin proof.

**Inferred risk:** A password/passkey session for a wallet-linked user could be presented as wallet authenticated. An end-to-end bypass has not been executed. Wallet switching, old-session acceptance, and revocation policy remain unknown and unapproved.

### F4 — Address-based OIDC subject consistency is unproven

**Status: Unknown. Verified test expectation; inferred likely gap.** The SIWE flow test expects UserInfo `sub` to equal `user.id` in `app/client-test-siwe/siwe-login.test.ts:141–147`. It separately asserts the verified wallet address at lines 69–70. The test does not assert that `user.id` equals that address.

No explicit wallet-address subject mapping was identified in `oauthProvider` configuration (`lib/auth.ts:312–390`). The custom access-token claims at lines 334–341 add an organization reference, not a demonstrated public OIDC address subject.

**Contract implication:** P1 requires the authenticated address as the public subject across clients. A framework user ID can be valid OIDC generally while failing this product requirement. Current test expectations suggest a mismatch but do not independently prove the emitted subject is a random internal identifier.

**Unknown:** Actual ID Token and UserInfo subjects, address matching/canonicalization, cross-client stability, and refreshed-token subjects. Exact `@better-auth/oauth-provider@1.7.11` implementation and executed evidence are unavailable. Access-token, introspection, and `client_credentials` subjects are not assumed to have OIDC end-user semantics; their behavior is unverified.

### F5 — SIWE validation is partially visible and partly delegated

**Status: Partial. Verified statically.** `createDemoSIWEPlugin` in `lib/siwe.ts:6–35` configures the expected domain, generates a nonce using 32 cryptographically random bytes, checks the SIWE URI origin, validates signature encoding, and calls viem `verifyMessage` with the normalized address. Exceptions return false.

`signInWithWallet` in `app/client-test-siwe/siwe-login.ts:30–70` obtains an injected wallet account and chain, requests a nonce, constructs a SIWE message, and requests `personal_sign`. Lines 49–58 include issuance time and five-minute expiration.

**Unknown:** Enforcement of signed-message domain, version, nonce binding/consumption, expiration and not-before bounds, and concurrent replay prevention depends on the uninspected `better-auth@1.7.11` plugin. Client-generated validity fields do not establish server-side enforcement.

Existing tests assert replay rejection (`siwe-login.test.ts:102–107`), wrong-signer rejection (`150–161`), wrong-domain rejection (`164–168`), and wrong-origin URI rejection (`171–186`). These were inspected, not executed. The application uses local signature verification; ERC-1271 support and chain-specific contract-wallet behavior are unproven.

### F6 — Wallet-owner application management is not established

**Status: Unknown.** The registration helper submits redirect URIs, scope, grant types, and response types (`app/client-test-siwe/oauth-flow.ts:96–113`) and uses the returned `client_id` separately from the user identity. This preserves distinct roles in the visible client flow.

However, no wallet-owner authorization or ownership mapping was identified in the inspected application configuration and registration wrapper. A search of application, library, data, and component source did not identify a dedicated wallet-owner client management layer. This does not establish that the framework lacks ownership features.

**Unknown:** Whether one verified owner can create and manage several applications, uniqueness and isolation of client records, cross-owner update/delete/secret access controls, and permission enforcement for non-session registration. No cross-owner negative test was executed. P3 cannot be certified, and F2 independently establishes a P5 configuration conflict.

### F7 — Service-account binding and published identity claims remain unverified

**Status: Unknown.** `app/client-test-siwe/siwe-login.test.ts:72–77` expects an unverified wallet-derived placeholder email. This is a favorable test expectation, not runtime evidence of actual OIDC claims.

No trusted binding between a verified wallet and an unrelated existing mailbox/chat/service account was established in the inspected SIWE/OAuth paths. The SCIM resolver uses its own verified issuer/subject and provisioning records (`lib/scim-demo-employee.ts:593–641`); that mechanism does not by itself establish a wallet binding.

**Risk and limits:** Placeholder emails must not become claims of mailbox ownership. Actual `email_verified` values in ID Tokens and UserInfo were not observed. No confirmed false verification claim or takeover is asserted. Optional service-account integration is not assumed to be a mandatory implemented feature, but P4's prohibition on unsupported ownership claims remains applicable.

### F8 — Standard protocol integration exists; independent conformance is unknown

**Status: Partial. Verified statically.** `createOAuthProof` in `app/client-test-siwe/actions.ts:13–28` generates random PKCE/state/nonce values and an S256 challenge. `oauth-flow.ts:174–193` builds an authorization request. `exchangeCode` at lines 214–232 uses form-encoded code exchange with the PKCE verifier. `fetchUserInfo` at lines 235–245 sends a bearer token without session cookies.

These are standard HTTP integration shapes; the reviewed token/UserInfo requests do not inherently require third-party applications to use the IdP's frontend libraries. The wallet frontend remains a separate injected-wallet walkthrough, while the main configured login page presents password/passkey methods (F1).

**Unknown:** Independent relying-party interoperability, discovery/JWKS behavior, ID Token verification, redirect validation, token reuse and refresh protections, actual claims, and deployed security controls. No OIDC conformance certification is implied. `client_credentials` is a separate application role and is not classified as a SIWE-only-login violation.

### F9 — No upstream patching observed

**Status: Compliant within inspected scope. Verified statically.** `lib/auth.ts` and `lib/siwe.ts` integrate Better Auth through imported plugins and configuration. No `patchedDependencies`, `patch-package`, or patch-path declarations were found in `package.json`, `pnpm-workspace.yaml`, or `pnpm-lock.yaml`.

This supports P7's maintainability preference for the inspected integration. It does not prove support for every desired extension, absence of deployment modifications, or exact upstream behavior. Framework gaps remain gaps; they do not authorize weakening the contract.

## Product Understanding Verdict

**The current repository does not satisfy approved Contract v1.1.** Direct source-level conflicts are established for independent non-SIWE login and unauthenticated client registration. The wallet walkthrough additionally treats account linkage as session-origin evidence, contrary to the explicit provenance boundary.

Address-based public subjects, owner isolation, complete SIWE enforcement, truthful emitted claims, and independent interoperability remain unverified. Existing tests are useful leads but cannot be reported as executed evidence. This report is an unreviewed assessment, not implementation authorization or a product decision.

## Unresolved decisions and unknowns

The contract's section 5 decisions remain unapproved:

- Canonical address representation and database matching.
- Consistent subject mapping for ID Token, UserInfo, and refresh; separate policy for other token subjects.
- Chain semantics, EOA/ERC-1271 support, and wallet linking.
- SIWE session provenance, wallet switching, revocation, and legacy-session treatment.
- Owner references, co-management, transfers, and administrative exceptions.
- Deployed controls and independent OIDC interoperability verification.

Exact locked upstream source, installed versions, runtime endpoint behavior, and negative-path test execution are principal evidence gaps. No recommendation in this assessment resolves those product decisions.
