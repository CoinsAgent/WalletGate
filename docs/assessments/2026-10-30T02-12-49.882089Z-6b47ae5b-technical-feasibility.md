# Technical Feasibility Assessment

## Question and contract constraints

Which supported technical approaches in the repository's locked Better Auth stack can address the latest compliance report's conflicts, partial requirements, and material unknowns?

Scope follows baseline findings F1–F8: SIWE-only authentication, trustworthy session provenance, address-based OIDC subjects, SIWE validation, wallet-owner client registration/management, truthful service identity claims, and interoperability. F9's maintainability constraint applies throughout. This is a feasibility investigation, not another full compliance scan or an implementation roadmap.

Contract v1.1 requires a verified Ethereum address as the same public OIDC subject across clients, SIWE-only end-user authentication, and wallet-authorized application ownership. Canonical address representation and several session/ownership policies remain unapproved. An internal user identifier can be valid OIDC generally while conflicting with this product. UserInfo subject consistency is required by [OIDC Core §5.3.2](https://openid.net/specs/openid-connect-core-1_0.html#UserInfoResponse); the requirement that the subject itself equal an Ethereum address is additional product policy. [ERC-4361](https://eips.ethereum.org/EIPS/eip-4361) specifies SIWE message structure and verification; the application's five-minute message lifetime is a separate policy choice.

## Verified behavior and technical limitation

**Verified:** `lib/auth.ts:110–120,145,195–300` still enables email/password, passkey, and SSO integration. `oauthProvider` selects `/sign-in` at lines 312–314. `app/client-test-siwe/wallet-client.tsx:48–51` still equates a linked SIWE account plus a session with a wallet session. The account selector lists device sessions without an origin filter (`app/(auth)/oauth/select-account/page.tsx:12–29`).

**Verified upstream:** BA `dist/plugins/siwe/index.mjs:63–123` validates before its session-creation call at lines 240–248. It creates an ordinary session for `user.id`; that call does not pass the authenticated address, chain, or an authentication-method override. BA `dist/db/internal-adapter.mjs:259–331` constructs session data and invokes session creation hooks. BA `dist/db/with-hooks.mjs:7–42` permits a create-before hook to reject creation or merge server-supplied fields.

**Limitation:** A linked account and display-only `customSession` callback are insufficient provenance. A session policy must also cover account selection, code/token issuance, refresh authorization, legacy sessions, and alternate session-creation routes. The complete enforcement of such a policy has not been demonstrated.

### Public OIDC subjects — baseline F4

**Verified upstream:** OP `dist/utils-vIo_wPv5.mjs:815–818`, `resolveSubjectIdentifier`, returns `userId` for public subjects; pairwise mode derives another identifier. OP `dist/introspect-B-5vOvYK.mjs:1399–1426`, `createIdToken`, resolves from `user.id` and pins that value as `sub`.

OP `dist/introspect-B-5vOvYK.mjs:13–51` strips reserved ID Token claims, including `sub`, from custom claims. Its public type declaration documents this restriction at `dist/oauth-DXiqbRzK.d.mts:1774–1792`. Therefore `customIdTokenClaims` cannot implement an address-subject override.

For UserInfo, `userNormalClaims` starts with `user.id` (`1146–1150`). `userInfoEndpoint` loads the user by access-token subject and re-pins `sub` after custom claims (`1230–1263`). Therefore `customUserInfoClaims` cannot override the subject either. Adding an address claim or changing only ID Token signing does not satisfy the required shared public subject.

**Verified cross-surface evidence:** JWT access-token construction uses `user?.id ?? client.clientId` (`1356–1369`). The common token issuance function calls `createIdToken` (`1786–1788,1876`). Introspection applies subject resolution to active payloads (`2505–2514`). These are distinct roles and paths; they do not imply a requirement that machine-token subjects be wallet addresses. Actual refresh execution, opaque/JWT parity, revocation, and migration behavior remain **Unknown**.

**Baseline refinement:** What was previously an unknown with a likely gap now has exact package-source evidence: configured public subjects are based on internal user identity, and ordinary claim callbacks cannot remap them. The repository does not configure address-based user IDs. CORE `dist/types/init-options.d.mts:359–374` documents random IDs as the default.

### Registration and owner isolation — baseline F2/F6

**Verified upstream:** OP `dist/authorize-CtCi8mAs.mjs:1792–1832`, `registerEndpoint`, distinguishes session, initial-access-token, and open registration. Only the session branch calls `assertClientPrivileges`. The privilege helper rejects absent sessions and invokes the configured callback (`1173–1183`). The API supports `clientPrivileges` actions including create/read/update/delete/list/rotate and privileged machine-scope configuration (`dist/oauth-DXiqbRzK.d.mts:1510–1531`).

Registration generates a separate client ID (`dist/authorize-CtCi8mAs.mjs:2010–2034`) and stores owner user ID or reference ID. Read, delete, and secret rotation compare owner user/reference (`2366–2379,2443–2458,2535–2550`); update has an explicit administrative exception for machine-scope-only configuration (`2467–2482`). **Verified limitation:** The initial-access-token callback can return an optional reference (`dist/oauth-DXiqbRzK.d.mts:1067–1075,1370–1398`). ## Supported extension mechanisms / candidate approaches

All candidate approaches and recommendations below are **unapproved**. They describe technical possibilities and constraints, not authorization or implementation steps.

### A. Restrict new authentication and bind provenance to sessions

**Supported mechanisms, Verified:** existing email/password configuration and plugin composition can restrict the configured login surface. CORE exposes `disabledPaths` and request hooks (`dist/types/init-options.d.mts:1522–1537`), database session create-before hooks (`1320–1329`), model additional fields (`193–195`), and plugin request hooks (`dist/types/plugin.d.mts:52–61`). BA's implementation actually merges create-before hook fields before persistence.

**Candidate, Inferred:** server-controlled session fields recording validated SIWE method, authenticated address/chain, and verification time can be attached on the successful SIWE session-creation path, with unrelated creation paths rejected or denied end-user authorization. A request path alone is not universal proof; the hook must be tied to the validation-before-session ordering and reject absent/untrusted context. Browser fields, linked accounts, and last-login display data cannot substitute.

**Trade-offs/Unknown:** persistence, session cache/secondary-storage behavior, account switching, renewal, session impersonation/transfer, old sessions, and token/refresh enforcement require consistent policy. Restricting only the frontend or only authorization-start leaves other routes unproven. **Verdict: Conditionally feasible**, medium confidence; configuration controls and hook primitives exist, but a complete policy is not verified.

### B. Choose an address-subject architecture

**Verified negative result:** direct `sub` replacement through `customIdTokenClaims` or `customUserInfoClaims` is **Not feasible in the checked version**, high confidence, for the source paths described above. The extension claim paths are also additive or reserved-filtered there. No proven public subject resolver was identified.

**Candidate 1, Inferred/Unproven:** represent each WalletGate user ID as its approved canonical wallet address so the provider's existing subject resolution remains consistent. CORE exposes user create-before hooks (`dist/types/init-options.d.mts:1272–1285`) and an ID-generation option (`359–374`); BA SIWE creates users only after verification (`dist/plugins/siwe/index.mjs:189–200`), through `createWithHooks` (`dist/db/internal-adapter.mjs:141–169`). These establish customization primitives, not a proven adapter-compatible address-ID implementation. IDs must derive from the validated message, never user name, ENS label, supplied email, or an arbitrary body field.

Trade-offs include existing-user foreign keys and token references, unique wallet mapping, address normalization, chain policy, prevention of alternate account creation, and any future multi-wallet policy. Callback-scoped state and adapter handling of supplied IDs were not proven. This candidate must not be treated as a migration decision.

**Candidate 2, Inferred:** a maintained upstream public subject-mapping feature or a separately evaluated standards provider could preserve internal user IDs while exposing address subjects. Neither is proven available for the checked package. A token-response/JWT rewrite alone is insufficient because UserInfo resolves internal users by token subject and additional surfaces depend on that identity.

**Verdict: Unproven**, medium confidence, for a complete supported address-subject solution with the existing internal identity model. This does not establish that all architecture choices are impossible. No upstream patch is recommended.

### C. Authorize wallet-owner registration and multiple applications

**Supported mechanisms, Verified:** `allowUnauthenticatedClientRegistration`, `allowDynamicClientRegistration`, `clientPrivileges`, `clientReference`, managed client APIs, and `validateInitialAccessToken` exist in OP 1.7.11. Owner references and independent client IDs are represented separately.

**Candidate, Inferred:** authenticated management with a trustworthy SIWE session and restrictive `clientPrivileges` can use session-user ownership or a server-derived wallet-owner reference. Returning an owner reference from `clientReference` can support stable owner mapping while keeping each client ID independent. The ordinary list/create shape supports multiple rows per owner; cross-owner isolation and races were not runtime tested.

Protected DCR via initial access tokens is an alternative only when issuance and validation are independently bound to approved wallet-owner authority and the callback returns the appropriate owner reference. It does not inherit session-hook checks. Denying administrative machine-scope exceptions and controlling client discovery are separate policy concerns. Client-supplied metadata is not owner proof.

**Trade-offs:** user-ID ownership minimizes extra mapping but requires a trustworthy one-wallet/user relation; reference ownership makes that relation explicit but needs authorization for management and lifecycle changes. Neither automatically approves co-management or transfer.

**Verdict: Conditionally feasible**, medium-high confidence. Exact supported APIs and owner comparisons are verified; wallet policy, deployed schema, and negative-path behavior remain unverified.

### D. Enforce complete SIWE validation through the existing callback

**Supported mechanism, Verified:** the application already supplies `verifyMessage` to the SIWE plugin (`lib/siwe.ts:16–33`), after upstream nonce/domain checks and before session creation.

VIEM `dist` equivalent `_esm/utils/siwe/validateSiweMessage.js:8–44` provides address/domain/nonce/scheme checks and rejects invalid or out-of-bound optional lifetime dates. `_esm/utils/siwe/parseSiweMessage.js:1–39` parses RFC-3339 dates and marks malformed ones invalid. The validator does not by itself enforce every required field, version, issuance-time policy, or whole-message grammar.

**Candidate, Inferred:** strict required-field/message validation plus explicit approved time, chain, and origin policy in the supplied callback can complement upstream nonce consumption without patching Better Auth. Local EOA verification and chain-aware ERC-1271 verification are different candidates; contract wallets require a chain/RPC trust policy that is not approved or proven here.

**Trade-offs/Unknown:** upstream consumes a nonce before all message/signature checks, so invalid attempts can burn a challenge; reusing that challenge is not a valid retry policy. Full grammar rejection and concurrent replay handling need executed evidence. **Verdict: Conditionally feasible**, medium confidence, for EOA-focused validation; **Unproven** for ERC-1271 support in the present integration.

### E. Truthful service claims and standard client integration

**Verified:** OP's standard email claim resolver reads `user.emailVerified ?? false` (`dist/introspect-B-5vOvYK.mjs:158–163`). The SIWE test expects a placeholder email and false verification (`app/client-test-siwe/siwe-login.test.ts:72–77`), but was not run. The public `customUserInfoClaims` API exists (`dist/oauth-DXiqbRzK.d.mts:1756–1772`); ordinary profile/email claims can be customized, subject to the subject restrictions already established.

**Candidate, Inferred:** suppressing placeholder email claims or retaining false verification is possible through claim/data policy. Neither proves ownership of an existing mailbox. A service-controlled binding between its existing account and the wallet is a separate trust mechanism. The SCIM resolver's issuer/subject binding (`lib/scim-demo-employee.ts:583–641`) demonstrates a distinct account-binding boundary, not a wallet binding.

**Verified:** the repository's token exchange and bearer UserInfo use standard HTTP (`app/client-test-siwe/oauth-flow.ts:214–245`). Third-party clients need not reproduce the IdP's wallet frontend. These integration shapes do not prove token-validation correctness or independent conformance.

**Verdicts:** truthful claim handling is **Conditionally feasible**, medium confidence; authentication of unrelated existing service accounts is **Unproven** without a trusted binding. Standards integration is **Conditionally feasible**, medium confidence, while deployed independent interoperability remains **Unproven**.
